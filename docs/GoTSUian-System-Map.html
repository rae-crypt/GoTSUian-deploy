The big picture

One Node server does two jobs at once: it hands the browser the HTML/CSS/JS files, and it answers the API calls those files make. Both come from the same address, which is why nothing in the frontend hardcodes a hostname.

In server/app.js, the line express.static(…/client) is what serves the frontend. Everything under /api/… is handled by a router instead. Because the page and the API share an origin, app.js can call /api/rides and /socket.io/… as plain relative paths — the same code works on your laptop, on your phone over Wi‑Fi, and on the live Railway URL with no changes.

There are three kinds of user, and they are kept genuinely separate: students (passengers) and drivers share the user_account login table, while admins live in their own administrator table entirely and log in through a different endpoint.

Why one server instead of two

Earlier the frontend ran on Live Server (a different port), so every API URL had to be written as http://localhost:3000/…. That broke the moment you opened the site from a phone. Serving both from one Express process removed the whole class of problem.

A request, end to end

Every single API call in this system follows the same six hops. Once you can trace one, you can trace all of them.

  1. The browser calls

    app.js runs fetch('/api/rides', { headers: getAuthHeaders() }). getAuthHeaders() attaches Authorization: Bearer <token> from sessionStorage.

  2. Express picks a router

    app.use('/api/rides', rideRoutes) sends it to rideRoutes.js, which matches the method + path to one controller function.

  3. The middleware checks the token

    authMiddleware runs jwt.verify(). Bad or missing token → 401 and the controller never runs. Good token → the decoded payload becomes req.user.

  4. The controller does the work

    Validates the input, then queries MySQL. It reads the user's identity from req.user — never from the request body.

  5. MySQL answers

    The pool in db.js lends a connection, runs the parameterised SQL, and returns rows to the callback.

  6. Reply, and tell everyone else

    The controller sends JSON back. If it changed a ride, it also fires a Socket.IO event so the other party's screen updates without refreshing.

Who you are (JWT)

There are no server-side sessions. Identity travels with each request as a signed token, and the server re-verifies it every time.

  • Logging in. The controller compares the typed password against the bcrypt hash with bcrypt.compare(). On success it signs a token containing accountId and role (admins get adminId instead), using JWT_SECRET, valid for JWT_EXPIRES_IN (7 days).
  • Storing it. The browser keeps the token in sessionStorage under authUser, alongside the display name and role.
  • Using it. Every protected call sends it as a Bearer header; the socket connection sends the same token in its handshake.
  • Trusting it. This is the important part: controllers use req.user.accountId, never an id from the URL or body. That's what stops one logged-in user from reading or cancelling someone else's rides just by changing a number.
Roles are enforced in two places

authMiddleware only proves who you are. Admin-only routes add a second requireAdmin check for role === 'admin', and ride acceptance separately requires the driver's account_status to be Active — a pending driver can browse requests but cannot take one.

The ride status machine

A ride moves forward through Pending → Accepted → Picked Up → In Progress → Completed. Three statuses end it early instead: Cancelled (either side backs out), Declined (the driver refuses — kept distinct so the passenger can be told), and Failed.

Live updates

Screens used to poll on a timer. Now the server pushes, and the browser reacts — which is why a driver accepting a ride updates the passenger's phone straight away.

Socket.IO rides on the same HTTP server and authenticates with the same JWT, sent through the connection handshake instead of a header. On connect, socket.js puts each user into rooms so a message can be aimed precisely:

  • account:<id> — a private room per user, for things only they should hear.
  • passengers — everyone browsing, for the "drivers available" count.
  • drivers — every driver, for newly posted ride requests.
Events and what the browser does with them

The events carry no data

Each event is a bare nudge meaning "something changed — go look again", and the browser re-fetches through the normal API. That keeps one source of truth (the database) instead of trying to keep a second copy in sync over the socket.

Flow: registration with email verification

A student can't create an account until they've proven they own the inbox. Here's the whole handshake.

  1. Email is checked for domain

    Only @student.tsu.edu.ph is accepted — plus @gmail.com temporarily, because TSU's mail filter is still silently dropping mail from the new domain.

  2. A code is generated and hashed

    Six random digits. The database stores only a bcrypt hash of it, never the code itself, with a 10-minute expiry. Any earlier code for that email is deleted first, so only the newest can work.

  3. The email goes out

    If the mail provider fails, the API returns 502 so the UI can say so honestly instead of pretending it sent.

  4. The code is verified

    /otp/verify compares the typed code against the hash. Wrong guesses increment attempts, and 5 failures burn the code. Success marks the row verified, which stays valid for a 15-minute grace window.

  5. The account is created

    registerStudent re-checks that verified row, hashes the password, and inserts user_account + student inside one transaction — so a half-made account can't exist. It then deletes the OTP row and issues a token, dropping the student straight into their dashboard.

Drivers register differently: no email code, but they upload a license file (handled by multer) and land as account_status = 'Pending'. They can log in and look around immediately — but accepting a ride is blocked until an admin approves them.

Flow: shared rides and the fare pool

The most intricate logic in the system, and the one worth understanding properly: how several students end up in one tricycle, and how the price per head is decided.

A pool is one tricycle trip on one route that up to four students split. The fare is per-head and drops as more people join:

₱60Solo
₱352 sharing
₱253 sharing
₱204 sharing

Booking a shared ride

  1. A lock is taken on the route

    The server takes a MySQL named lock keyed to a hash of pickup + dropoff. This is essential: without it, two students booking the same route in the same instant both check "is there an open pool?", both see "no", and both create one — permanently splitting a group that should have been together.

  2. Find a pool, or start one

    It looks for the oldest Open pool on that exact route with fewer than 4 riders. If none exists, it creates one.

  3. The rider is inserted

    If a driver already claimed the pool, the new rider joins as Accepted straight away — otherwise as Pending.

  4. The fare re-settles

    Once a driver is committed or the pool hits four, the per-head fare is recalculated and written to every rider in the pool. A full pool is also marked Closed.

  5. Lock released, everyone notified

    The lock is freed and a socket event tells the others in the pool (or all drivers) to refresh.

A driver accepting one

  • The driver must be Active, and must not already be on another trip.
  • A pool needs at least 2 riders — a 1-person "shared" ride is just a Solo at a worse price, so it's refused.
  • Claiming is guarded by driver_account_id IS NULL, so if two drivers tap Accept at the same moment, only the first succeeds and the second is told the ride was taken.
  • Accepting with fewer than 4 riders doesn't close the pool — more students can still join the same tricycle, and the fare keeps dropping, until it fills or the driver marks Picked Up and departs.
Why "Open" doesn't mean "unclaimed"

A pool's status tracks whether it still takes new riders; driver_account_id tracks whether a driver owns it. Conflating the two caused a real bug: a pool that filled to 4/4 on its own was marked Closed, and the accept check read that as "already taken" — so no driver could ever accept it.

How the frontend is organised

One script runs all 13 pages. The conventions below are what keep that manageable.

Every page loads the same JavaScript

client/js/app.js is shared by every page. It works out where it is from <body data-page="…">, and — more often — from whether a given element exists at all. Nearly every function starts with a guard like if (!el) return;, so it simply does nothing on pages it doesn't apply to.

Two families of function

  • setup…() attaches event listeners. These run once, on DOMContentLoaded — calling one twice would double-fire every click.
  • render…() re-reads state and repaints. These are safe to call any number of times, which is exactly why socket events can just call them again.

refreshAuthState() bundles the render calls that depend on login state, and runs on load, after login, and when a page is restored from the back/forward cache.

Styling

Each page has its own stylesheet, with theme.css linked last everywhere as a shared override layer. Because browsers cache aggressively, every link carries a version query — rules.css?v=62 — bumped whenever that file changes. It's the difference between a fix going live and you staring at an old cached copy.

A trap worth remembering

passenger.html, passenger-profile.html and passenger-bookings.html all share data-page="passenger". It identifies the section, not the file — so styling just one of them needs an extra class on that page's body.

Running in production

What's different between your laptop and the live site.

  • Host. Railway runs the Node process and a MySQL service side by side. The app is served at gotsuian.up.railway.app; the database is the gotsuian_db schema on the MySQL service.
  • Deploys. Pushing to the deploy repository triggers a rebuild — there's no separate build step, since the frontend is plain HTML/CSS/JS.
  • Configuration. Everything secret comes from environment variables: DB_HOST, DB_USER, DB_PASSWORD, DB_NAME, DB_PORT, JWT_SECRET, JWT_EXPIRES_IN, and the mail credentials. Locally these live in server/.env, which is never committed.
  • Two IPv4 details. app.js sets dns.setDefaultResultOrder('ipv4first') because Railway containers can't route outbound IPv6 — without it, sending mail times out. And connecting to the database from your own machine needs the public proxy host from Railway, not the internal .railway.internal one.
  • Connection pooling. db.js uses a pool rather than one long-lived connection, which used to die on idle timeout and take every later query down with it until the process restarted.
